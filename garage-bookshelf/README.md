## 版本目录规约（从v5开始）

从v5开始，每个版本都按下列职责组织文件。新建v6、v7及后续版本时，必须沿用这些目录名称和用途；新增目录须在对应版本的README中说明职责。
本README维护版本导航和通用规约，具体版本的设计变更统一记录在该版本的`CHANGELOG.md`中，例如[v5/CHANGELOG.md](v5/CHANGELOG.md)。

下表路径均相对于各版本根目录（如`v5/`、`v6/`）：

| 文件或目录 | 用途与约定 |
|---|---|
| `README.md` | 稳定的版本入口：说明产品组成、读者路线和资料查找规则；具体款式与车型由组件索引维护。 |
| `PROJECT_STATUS.md` | 按组件汇总验证进展、适用范围与未解决事项，链接组件索引；不逐款列举名称、数量或验证文件。 |
| `CHANGELOG.md` | 设计与维护沿革：按日期记录变更及影响；同一事件已有记录时补充原条目，不重复新增。 |
| `cad/` | 正式总装CAD及模型规范；总装用于整体和接口验证，各组件索引明确唯一源文件。 |
| `cad/main/` | 主体CAD入口，包括两块广告牌的固定结构，不含可换文字载板。 |
| `cad/sign-carriers/` | 上方、右侧文字载板的源文件索引及新增定制款。 |
| `cad/parking-inserts/` | 通用底脚和车型卡槽的源文件索引及新增车型款。 |
| `src/garage_bookshelf/` | 可复用的建模、外观、验证、导出和打印逻辑，供工具共用。 |
| `tools/` | 验证、导出、渲染、排盘和打包等命令入口；一次性迁移脚本须注明用途及执行状态。 |
| `tests/` | 工具与工作流程检查，验证输出路径、文件保护和数据一致性等约束。 |
| `pyproject.toml` | Python工具包配置，与`src/`、`tools/`和`tests/`配套维护。 |
| `assets/` | 建模和打印所依赖的固定输入资源，如冻结字形、打印预设；生成工具不得覆写这些输入。 |
| `docs/` | 维护者通过`maintenance.md`修改和生成，组装者通过`assembly.md`、`customization.md`拼装和提出定制需求；设计与接口规范共同引用。 |
| `docs/interfaces/` | 文字载板与车型卡槽的唯一接口和验证规范；车型卡槽采用BMW Z4 E89实测四轮弧形槽方法。 |
| `printing/` | 当前文件入口、排盘计划和带哈希的组件清单；直接分为以下三类，不设current或日期交付层。 |
| `printing/main/` | 主体打印文件及单独标明的个人设置；不含可换文字载板和车型卡槽。 |
| `printing/sign-carriers/` | 按上方／右侧及款式保存文字载板，说明接口版本和试装状态。 |
| `printing/parking-inserts/` | 按车型及修订保存卡槽，说明适用车型、打印设置和试配状态。 |
| `printing/<组件>/<款式路径>/evidence/` | 当前款式的原始验证证据：CLI日志、冻结打印配置、检查用网格及必要的生成工具快照；随对应交付保存。 |
| `studies/` | 结构分析、车型适配和配合试件；每项研究独立保存说明、输入与结论，验证后再决定是否并入正式设计。 |
| `build/` | 可再生成的导出、预览、切片、日志及候选交付包，按`build/<run-id>/`分次输出；临时文件放`build/tmp/`。除目录说明外不纳入Git。 |
| `archive/` | 历史CAD、旧方案、旧工具、快照和报告；保留原始来源与验证结论，不作为当前设计或打印入口。 |

维护及新建版本时还必须遵守：

1. 版本根目录只放入口文档和项目配置，模型、脚本、打印文件、研究资料与生成结果分别归入上述目录。
2. 新版本的正式CAD、工具和输出路径必须指向本版本；不得由新版本工具改写旧版本目录或历史归档。
3. 自动生成和打包先写入新的`build/<run-id>/`，不得覆盖已有结果或人工3MF；确认交付后按组件保存到`printing/`，更新文件清单、源CAD哈希、打印参数和验证记录；旧交付完整归档。
4. 研究试件与正式交付分开保存；历史验证保留当时的源版本和结论，不得直接当作当前设计的验证结果。
5. 设计或打印交付变更时，更新相关组件索引、文件清单和说明，并在`CHANGELOG.md`记录变更。验证结论、已知问题或待办变化时更新`PROJECT_STATUS.md`；产品组成、阅读路线或查找规则变化时才更新版本`README.md`，不向其中追加具体款式或逐日变更。本总览维护通用规约。
6. 新增文字或车型通常只增加独立定制款；接口不兼容时必须建立新接口版本，注明兼容主体。组装者与维护者共用接口规范，不重复维护两套尺寸和检查规则。

## 当前交付的证据存放规约

新增或更新文字载板、车型卡槽时，按以下方式交付：

1. 自动生成先进入新的`build/<run-id>/`。确认保留的当前款式，原生CAD及冻结字形等建模输入以`cad/<组件>/<款式路径>/`为唯一源文件位置。
2. `printing/<组件>/<款式路径>/`保存3MF、款式`README.md`、预览、`validation.json`和`slice-result.json`；原始CLI日志、实际使用的冻结打印配置、检查用STL及必要的生成工具快照放在其`evidence/`内。文字载板的款式路径为`<upper或side>/<款式>`，车型卡槽为`<车型>/<修订>`。
3. `validation.json`记录输入总装版本、定制CAD与3MF哈希、生成工具版本、验证执行日期、检查范围和实物验证状态。报告的`files`中每个带哈希的交付文件必须通过`artifact_locations`给出相对于版本根目录的实际保存路径；发布时只补充位置元数据，不把复制或整理日期改成验证执行日期。打印交付及证据文件的哈希登记在`printing/catalog.json`中。
4. 当前款式的说明和组件索引必须能直接找到源文件、验证记录与实物反馈，不能依赖被Git忽略的`build/`。日志中的工具警告、模型警告和实物试配结果分别记录，切片成功不代表实物试装通过。
5. `archive/`保存已被替换的旧交付及其证据，原文件与哈希保持不变。规约建立前已归档的基线和款式证据保留原址，由当前索引或验证报告显式引用；新交付按上述目录组织，不再以日期归档目录充当当前款式的证据位置。

## 状态汇总与更新规约

文档按以下职责维护，避免新增款式时在多处重复登记：

| 信息 | 唯一维护位置 | 更新方式 |
|---|---|---|
| 产品组成、读者路线和查找规则 | 版本`README.md` | 入口或组织方式变化时更新；不写具体款式与款式数量。 |
| 全部款式、文件与验证入口 | 对应组件的CAD／打印索引 | 新增、替换或撤下款式时更新；引用该款说明和验证记录。 |
| 单款的验证范围、已知限制和实物反馈 | 对应打印款式的`README.md`及验证记录 | 写明适用修订与证据；反馈针对哪个版本就记在哪个版本，不自动推广到其他款式或修订。 |
| 组件层面的验证进展与未解决事项 | `PROJECT_STATUS.md` | 按主体、文字载板、车型卡槽汇总，只链接组件索引；不复制完整款式清单、数量或逐款报告链接。具体未解决问题可点名并链接该款说明。 |
| 一次设计或维护变更的经过与影响 | `CHANGELOG.md` | 按日期和事件记录，保留历史结论，不作为当前款式索引。 |

新增款式时必须更新组件索引、款式说明、文件清单及变更记录。仅增加款式且组件层面的验证范围、问题或待办未变时，无须改动`PROJECT_STATUS.md`和版本`README.md`。更新状态汇总时保留资料核对日期，并区分实际完成、缺少反馈记录和仍待验证。
